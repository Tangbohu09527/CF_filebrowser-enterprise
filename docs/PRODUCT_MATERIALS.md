## Implemented interface

`POST /api/resources/products` uses the normal authenticated resource and audit middleware. `server.productMaterialsUsers` is an exact service-user allowlist, default empty. Existing user permissions, token intersection, current Source/Scope and per-path checks still apply. No model receives a service token or host path.

- `inspect`: bounded ZIP metadata and streamed member CRC/SHA-256 validation.
- `preview`: one selected PNG/JPEG member, verified against the inspected package. The trusted adapter invokes the installed native vision tool and includes the actual image in the model result.
- `import`: explicit brand/product/specification/version, archive digest and a complete member classification/evidence map. Missing or ambiguous identity is not guessed; `pending` is an explicit category. It retains the original ZIP and creates a new version. It does not overwrite an employee version.
- `export`: a confirmed complete version and explicit categories. Every selected source is authorized, frozen, checked and packed. The ZIP is reread to compare all members, then sources are rechecked. Stable temporary metadata makes identical export retries byte-identical. Source metadata is unchanged.

Limits are coordinated at 128 MiB compressed/upload/output, 512 MiB expanded, 32 MiB per member and 2,000 entries, with a 200:1 expansion bound. ZIP links, special files, encryption, path traversal, collisions and malformed length/CRC are rejected. Normal Chinese names, spaces and parentheses survive. Product/version/output labels also reject Windows reserved names, control/format characters and illegal filename characters.

Import publishes `product-materials.pending.json` first and `product-materials.json` last. An existing version requires an exact matching pending intent. Retries validate all files, including after process restart. New publication uses exclusive directory reservation and hard-link no-replace publication; unsupported filesystems fail closed. Changed bytes return 409. Partial imports remain accurately pending and are not deleted or advertised complete. This protects normal scoped API activity; it does not claim to defeat an administrator replacing filesystem parents outside the service.

## Hermes and Gateway contract

Two opt-in tools are registered through the normal plugin loader:

1. `filebrowser_ingest_product_zip`: accepts only the current attachment ID, resolves the active host binding, verifies the inbound workcopy and streams it through the Go client to the scoped enterprise incoming directory. The original upload is retained. It returns an inspected manifest, not a host path.
2. `filebrowser_product_materials`: list/search/stat/checksum/mkdir, inspect/preview/import/export and explicit single-file organization, fixed configured enterprise source and root. A trusted current Gateway task is required, with an exact allowlist of enterprise identity, thread, source account, private chat, Profile reference and revision. Every subprocess is bounded and checks task liveness while running. Model input cannot supply an executable, token, URL, filesystem path or `apply` switch.

Generated export descriptor fields are `source`, `path`, `name`, `mime_type=application/zip`, `size_bytes`, `sha256`, and `manifest`. The already loaded Gateway return plugin registers an opaque current-task `file_ref`. `cf_return_current_chat` then imports the ZIP server-to-server from a fixed TLS FileBrowser source/root. ZIP output is not routed back through the AI host. Inbound staging still uses the existing protected host workcopy once; formal extraction, archive and query happen on FileBrowser. Old attachment handles and original-only followup capabilities cannot authorize a new ZIP.

A normal user can ask to preserve and classify a product package, then ask to export the latest *confirmed* product version. Tools expose real listings and preview content; product/version ambiguity must be clarified. This candidate does not imply support for arbitrary natural-language attachment-reference resolution or full chat history retrieval.

## Single-file organization and recovery

The follow-on `organize` action implements copy, move, same-directory rename, replacement, recoverable deletion and restore for one bounded regular file. The model uses the existing product tool; its Source and `.recovery` root are fixed by trusted configuration. `checksum` obtains the actual version digest before mutation. Destructive operations require current Modify/Delete permissions in addition to scoped Create/Browse/Download; a token cannot preserve revoked account authority.

Each action freezes the original digest and immutable intent, publishes a before-image, then uses the existing platform no-replace rename primitive to retain the original before publishing the destination. A differing destination is never overwritten. Replacement requires a separately authorized replacement path and digest. Deletion retains the bytes; it is not permanent removal. Recovery records include actor, source, original/destination mapping, digests and completion state. Restore requires the same actor and exact prior recovery mapping, and still cannot overwrite a new differing employee file. Partial operations retain evidence and before-images; retries validate the same persisted intent after process restart. There is no automatic rollback across an unknown outcome.

The scoped tool prevents organizing its own recovery records. The files remain under the normal file-service account and filesystem protections; this is recovery, not a claim that a fully privileged filesystem operator cannot tamper with evidence. An altered before-image fails digest verification. Tests cover real authenticated/audited HTTP copy/move/rename/replace/delete/restore, conflicting targets, wrong expected versions, account revocation, foreign-actor restore, pending/replacement recovery after lost in-memory locks and employee edits after snapshot. Existing unrestricted PATCH/DELETE is not exposed as an alternative. Moving or replacing a member of an immutable published product version deliberately makes subsequent export fail its frozen manifest check; copy is preferred when preserving that version.

## Dedicated export reader bootstrap

The official operator CLI adds `set service-reader --username NAME --source SOURCE --scope /existing/narrow --password-stdin -c config.yaml`. It accepts one bounded 32–256-byte printable ASCII password line on standard input. Passwords do not enter arguments or environment variables and are not included in the result. It creates only a new password account, through normal storage, with Browse, Download and session API capability; no Admin, Create, Modify, Delete, Share or Preview. An existing username or uncertain lookup refuses without resetting anything. The source must exist and the explicit non-root scope must already be a contained directory. The process requires an existing database. Stop the service and verify a restorable backup before this exclusive-database command; it is not an online admin API or a root credential exposed to the model.

After controlled restart, authenticate normally and create a full API token through the existing session-only token endpoint with `permissions=browse,download`. A full token inherits the current account scope; it has no independent Source/Scope. The token itself must have API disabled. The reader account therefore has its own precise single scope; production verification must check the token/account intersection, deny writes and deny access outside that scope. Downloads under this reader are scope-relative: a producer descriptor rooted at `/商品资料/新谷力` must be checked against that exact prefix before converting to the reader's relative request path. No token signing, direct database edits or current account reset are introduced.

`serviceScopeLocked` is a forward-compatible persisted user boolean, default false for existing accounts. Only this new-account CLI sets it. User creation/update APIs cannot set or clear the flag; ordinary non-admin updates still cannot change scopes or permissions. Startup retains the explicit service scope instead of appending default-enabled sources. Removing permissions remains effective. Tests run the actual CLI in a child process against an isolated existing database, verify password hashing, exact permissions/scope, preservation of an unrelated sentinel and refusal to recreate/reset the account; storage and startup tests cover lock immutability, extra-source defaults and revocation. A test fixture initially used `.json`, which the existing YAML-directory combiner ignored; changing the fixture to the supported `.yaml` entry resolved it.

There is no schema migration, but older binaries do not know the scope-lock contract. Do not return an old server binary to service with this enabled reader account: first revoke its token and remove/disable the new account through a verified supported operation, or retain the new binary. A generic schema-downgrade or database replacement would destroy unrelated later records and is not a rollback procedure. This candidate adds the bootstrap capability; actual account creation, token issuance and production checks are operator evidence, not implied by local tests.
